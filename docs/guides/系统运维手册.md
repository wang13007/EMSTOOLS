# EMS 售前调研工具系统运维手册（当前版本）

更新时间：2026-05-09

## 1. 运行架构

- 前端：React + Vite 静态站点
- 数据与鉴权：Supabase
- AI 报告：Gemini API（可选）

## 2. 运维基线

### 2.1 环境要求

- Node.js 18+
- npm 9+
- 可访问 Supabase

### 2.2 常用命令

```bash
npm install
npm run dev
npm run build
npm run preview
npm run lint
```

## 3. 初始化与升级

### 3.1 新环境初始化

1. 配置 `.env.local`
2. 执行 [`supabase-init.sql`](../../supabase/sql/supabase-init.sql)
3. 启动项目并验证核心路径

### 3.2 老环境修复

执行 [`supabase-repair-existing.sql`](../../supabase/sql/supabase-repair-existing.sql)，用于修复：

- 字段类型不一致
- 外键缺失
- 历史脏数据

### 3.3 审计日志生产加固

1. 在 Supabase SQL Editor 执行 [`supabase-audit-hardening.sql`](../../supabase/sql/supabase-audit-hardening.sql)，为 `system_logs` 增加 `request_id`、`user_agent`、`source`、`metadata`、`previous_hash`、`integrity_hash` 字段与索引。
2. 在 Supabase Edge Functions Secrets 配置：
   - `SUPABASE_URL`
   - `SUPABASE_SERVICE_ROLE_KEY`
   - `AUDIT_LOG_HMAC_SECRET`，使用 32 字节以上随机值。
   - `AUDIT_ALLOWED_ORIGINS`，生产域名白名单，多个域名用英文逗号分隔。
3. 部署 Edge Function：

```bash
supabase functions deploy audit-log
```

4. 前端生产环境建议配置 `VITE_AUDIT_LOG_STRICT=true`。开启后如果 Edge Function 不可用，前端不再降级直写 `system_logs`，避免绕过服务端 IP 采集和哈希链。
5. 加固脚本会撤销 anon/authenticated 对 `system_logs` 的写权限，只保留读权限；日志写入必须走 service role 的 Edge Function。
6. 若仍需本地开发兼容，可不配置 `VITE_AUDIT_LOG_STRICT`，此时函数不可用会尝试降级为浏览器直写；若已执行加固脚本，浏览器直写会被数据库拒绝。

## 4. 发布流程（建议）

1. 本地执行 `npm run lint` 与 `npm run build`
2. 合并到主分支
3. 由 Cloudflare Pages 自动部署
4. 发布后执行回归检查清单

## 5. 监控与巡检

### 5.1 日常巡检项

- Supabase 项目状态
- 关键表读写是否正常
- 登录、调研提交、报告查看是否可用
- 消息与日志是否持续更新
- `system_logs` 是否持续产生 `login/survey/user/system` 四类记录
- 日志页 `/settings/logs` 是否能显示操作人、结果与时间倒序列表

### 5.2 故障定位顺序

1. 浏览器控制台报错
2. Supabase 查询与策略
3. 环境变量配置
4. 第三方 API（Gemini）可用性

### 5.3 日志审计验证

1. 使用管理员账号登录系统，确认 `system_logs` 新增一条 `login` 成功记录。
2. 故意输入错误密码登录，确认新增一条 `login` 失败记录，且日志内容不包含密码。
3. 新建、更新或删除用户/角色，确认新增 `user` 类型记录。
4. 新建、填写、提交、删除调研或生成报告，确认新增 `survey` 类型记录。
5. 导入/删除模板或标记消息已读，确认新增 `system` 类型记录。
6. 进入 `/settings/logs`，检查页面可按类型筛选并显示操作人。

说明：生产环境应以 `audit-log` Edge Function 写入为准。函数会从 `cf-connecting-ip`、`x-forwarded-for`、`x-real-ip` 等请求头提取真实客户端 IP，并用 `AUDIT_LOG_HMAC_SECRET` 计算 `integrity_hash`，通过 `previous_hash` 形成日志哈希链。当前自定义 localStorage 登录态不是服务端可验证身份凭证，因此操作人仍来自前端上报的 `operator_id`；若要实现强身份审计，需要同步迁移到 Supabase Auth、Edge Function 会话校验或独立后端认证。

## 6. 备份与恢复

- 使用 Supabase 自动备份
- 关键节点手工导出 SQL/CSV
- 恢复后优先验证 `users`、`survey_forms`、`survey_reports` 三表一致性

## 7. 安全要求

1. 严禁在前端暴露高权限密钥
2. RLS 策略需按角色和数据归属最小化
3. 定期轮换密钥并更新部署环境变量
4. 定期审计异常登录、越权访问与关键写操作
5. 日志写入失败不阻断业务，运维需通过巡检及时发现 `system_logs` 停止增长的问题

## 8. 风险项与改进建议

- 当前前端存在 service role 回退密钥逻辑，建议尽快移除
- AI 报告生成建议迁移服务端，避免密钥暴露
- 建议补充自动化测试与发布前检查脚本
- 建议将认证、关键写操作和审计日志统一迁移到后端/Edge Functions，避免前端自定义会话导致审计可信度不足
- 已提供 `audit-log` Edge Function 作为审计写入入口；下一步建议把用户身份校验也迁入服务端，使 `operator_id` 不再依赖前端上报
