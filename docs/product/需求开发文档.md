# EMS 售前调研工具 PRD（实现对齐版）

更新时间：2026-05-09
版本基线：`master` 分支

## 1. 产品定位

EMS 售前调研工具用于标准化售前调研、结构化沉淀客户信息、自动生成可交付报告，提升售前效率并降低沟通成本。

## 2. 用户与权限

### 2.1 用户角色
- 内部用户：管理员、售前工程师等。
- 外部用户：客户用户。

### 2.2 访问控制
- 未登录访问受保护路由时，跳转 `/login?redirect=...`。
- 外部用户仅允许：
  - `/customer-survey/list`
  - `/surveys/fill/:id`
  - `/authorized/surveys/fill/:id`
- 外部用户访问其他路由，重定向到 `/customer-survey/list`。

## 3. 功能需求详细设计

说明：当前实现无独立后端网关，接口层为前端 Service 对 Supabase 的封装调用。

### FR-01 登录与注册

#### 页面描述
- 登录页：`/login`
- 注册页：`/register`（外部用户）

#### 交互描述
- 登录输入用户名、密码后提交。
- 注册输入姓名、用户名、手机号、邮箱、密码、确认密码。
- 登录后根据 `redirect` 参数回跳目标页，否则进入 `/`。

#### 业务规则
- 登录失败条件：用户不存在、密码不匹配、状态异常。
- 授权链接场景支持“自动创建外部用户”（可选）。
- 注册仅创建外部用户，需绑定外部角色。
- 登录成功写入 `ems_user`、`ems_token`，并更新最近登录时间。

#### 表结构设计
| 数据表 | 主键 | 关键字段 | 说明 |
| --- | --- | --- | --- |
| `users` | `id` | `user_id`, `username`, `user_name`, `name`, `password_hash`, `type`, `user_type`, `role_id`, `role_ids`, `status`, `last_login_time` | 账号主体、登录校验、用户类型与角色关系 |
| `roles` | `id` | `name`, `permissions`, `type`, `user_type`, `status` | 角色定义与权限承载 |

#### 接口设计
- `authService.login(data, options?)`
  - 入参：`username/password`，可选 `autoCreateExternalIfNotExists`
  - 出参：`{ user, token }`
- `authService.register(data)`
  - 入参：注册信息
  - 出参：`{ user, token }`
- `authService.logout()`、`authService.getCurrentUser()`

### FR-02 调研列表管理

#### 页面描述

- 外部用户列表仅显示本人可访问表单。
- “重填”将状态回退到草稿并清空报告生成状态。
- “删除”执行物理删除。

#### 表结构设计
| 数据表 | 主键 | 关键字段 | 说明 |
| --- | --- | --- | --- |
| `survey_forms` | `id` | `name`, `customer_name`, `project_name`, `industry`, `region`, `status`, `report_status`, `creator_id`, `submitter_id`, `pre_sales_responsible_id`, `data`, `create_time`, `update_time` | 调研列表主数据源 |
| `users` | `id` | `id`, `user_id`, `user_name`, `name`, `username` | 用于创建人/提交人/负责人姓名映射 |

#### 接口设计
- `surveyService.getSurveys()`
- `surveyService.updateSurvey(id, payload)`（重填）

### FR-03 新建调研

#### 页面描述
- 页面路径：`/surveys/new`
- 支持两种模式：直接创建、生成外部填写链接。

#### 交互描述
- 填写基础信息：表单名、客户、项目、行业、区域、售前负责人、模板。
- 模式为“外链”时，创建后展示并支持复制授权 URL。

#### 业务规则
- 当前登录用户 ID、售前负责人 ID 必须是合法 UUID。
- 售前负责人从“售前工程师角色用户”中筛选。
- 创建时预写模板初始字段到 `data`。
- 外链模式写入 `data.external_link_enabled=true`。

#### 表结构设计
| 数据表/存储 | 主键/Key | 字段 | 说明 |
| --- | --- | --- | --- |
| `survey_forms` | `id` | `name`, `customer_name`, `project_name`, `industry`, `region`, `template_id`, `status`, `report_status`, `creator_id`, `submitter_id`, `pre_sales_responsible_id`, `data` | 新建调研核心落库表 |
| `localStorage` | `ems_last_created_survey_id` | `surveyId` | 创建成功后的本地回填 ID |

#### 接口设计
- `roleService.getRoles()`、`userService.getUsers()`（负责人候选）
- `surveyService.createSurvey(payload)`
- 失败兜底：创建后再次调用 `surveyService.getSurveys()`反查最新记录

### FR-04 调研填写与自动保存

#### 页面描述
- 页面路径：`/surveys/fill/:id`、`/authorized/surveys/fill/:id`
- 按模板动态渲染分组字段与可见性规则。
- 页面顶部采用统一详情头部，承载标题信息、表单/报告页签、操作按钮和状态提示。

#### 交互描述
- 字段类型支持：文本、数字、单选、多选、文本域。
- 顶部展示表单名称、客户、项目、行业、区域等摘要信息。
- 已生成报告时，顶部提供“表单 / 报告”页签，与报告详情页保持一致。
- “保存草稿”手动保存。
- 自动保存：输入后约 1200ms 触发。
- 自动保存结果在顶部提示区反馈。
- 返回列表前自动尝试保存。

#### 业务规则
- 已完成表单只读。
- 授权链接访问时，若外部用户尚未授权，会自动尝试绑定。
- 预填字段（客户、项目、区域、行业等）只读不可改。
- 保存时更新 `submitter_id`、`status`、`data`。

#### 表结构设计
| 数据表/存储 | 主键/Key | 字段 | 说明 |
| --- | --- | --- | --- |
| `survey_forms` | `id` | 读取：`id`；更新：`data`, `status`, `report_status`, `submitter_id`, `update_time` | 填写态与草稿持久化 |
| `survey_forms.data` | JSONB 子字段 | `external_link_enabled`, `external_access_user_ids` | 授权外链访问控制 |
| `localStorage` | `ems_surveys` | `SurveyForm[]` | 前端本地缓存与详情回显 |

#### 接口设计
- `surveyService.getSurveyById(id)`
- `surveyService.grantExternalAccessByAuthorizedLink(id)`
- `surveyService.updateSurvey(id, payload)`
- `userService.getUsers()`（售前联系人补充）

### FR-05 提交并生成报告

#### 页面描述
- 入口：填写页统一详情头部的操作区“提交并生成报告”。
- 成功后跳转报告详情页。

#### 交互描述
- 点击提交后展示“AI 分析中”状态。
- 自动先做未保存草稿提交。
- 失败弹窗提示。
- 生成成功后，用户可通过统一头部中的“表单 / 报告”页签在两页间切换。

#### 业务规则
- 若草稿自动保存失败，阻止提交并提示先保存。
- 提交后写入：`status=completed`、`report_status=generated`、`data.submit_time`。
- AI 报告优先 Gemini，未配置 Key 时使用回退报告。

#### 表结构设计
| 数据表/存储 | 主键/Key | 字段 | 说明 |
| --- | --- | --- | --- |
| `survey_forms` | `id` | `status`, `report_status`, `data.submit_time`, `submitter_id` | 提交状态与提交时间落库 |
| `localStorage` | `ems_reports` | `{ [surveyId]: ReportBundle }` | 报告包缓存（AI + 模板 + 匹配 + 联系人） |

#### 接口设计
- `generateEnergyReport(form)`
- `buildReportBundle(form, aiReport, preSalesContact)`
- `surveyService.updateSurvey(id, payload)`

### FR-06 报告详情

#### 页面描述
- 页面路径：`/reports/:id`
- 页面顶部与调研填写页共用同一套详情头部设计语言。
- 顶部提供“表单 / 报告”页签；报告内容区提供“AI 诊断报告 / 模板报告”切换。
- 报告类型切换：AI 诊断报告 / 模板报告。
- 支持分享链接、导出 PDF。

#### 交互描述
- 页面加载时读取本地报告包。
- 若数据结构不完整，自动重建报告并回写。
- 顶部展示项目、客户、行业、区域、生成时间等摘要信息。
- 顶部操作区包含返回列表、分享链接、导出 PDF，排布与表单页统一。
- 点击“链接分享”复制 URL。
- 点击“导出PDF”导出当前视图内容。
- 导出时隐藏顶部页签与操作按钮，仅保留报告内容主体。

#### 业务规则
- 找不到调研或报告时，分别跳转列表或填写页。
- 联系人信息不足时自动补查用户表并补全。
- 导出文件名按“项目名 + 报告类型”生成。
- 报告输出需包含模板识别能力标签、能力匹配计算规则、综合解决方案清单。
- 历史报告若缺少新结构（`capabilityMatchingContext`、`solutionCatalog`），页面加载时自动重建并回写。

#### 表结构设计
| 数据表/存储 | 主键/Key | 字段 | 说明 |
| --- | --- | --- | --- |
| `localStorage` | `ems_surveys` | `SurveyForm[]` | 报告详情页加载调研基础信息 |
| `localStorage` | `ems_reports` | `ReportBundle` | 报告正文与图表主来源 |
| `users` | `id` | `phone`, `email`, `name`, `username` | 售前联系人补齐信息 |

#### 接口设计
- `buildReportBundle(...)`（重建）
- `userService.getUsers()`（联系人补全）
- `html2canvas + jsPDF`（导出）

- 结果受约束：`成功/失败`。
- 服务层负责记录关键用户行为，不依赖日志页面手工生成。
- 记录范围包括登录成功/失败、注册成功/失败、退出登录、用户与角色增删改、调研表单创建/更新/删除、外部授权链接、报告保存、模板导入/删除、消息已读等操作。
- 每条日志写入 `operator_id`、类型、内容、结果、创建时间和客户端地址提示。
- 日志查询时根据 `operator_id` 关联 `users` 表补齐操作人名称；无法识别时显示“系统/未登录用户”或“未知用户”。
- 日志写入失败不阻断原业务流程，但必须输出控制台错误，便于运维定位。
- 生产环境日志写入由 Supabase Edge Function `audit-log` 承担，前端调用函数，不直接写审计表。
- Edge Function 使用服务端 `SUPABASE_SERVICE_ROLE_KEY` 写入 `system_logs`，从请求头提取真实客户端 IP，并写入 `request_id`、`user_agent`、`source`、`metadata`。
- Edge Function 使用 `AUDIT_LOG_HMAC_SECRET` 计算 `integrity_hash`，并记录上一条审计日志的 `previous_hash`，形成防篡改哈希链。
- Edge Function 可通过 `AUDIT_ALLOWED_ORIGINS` 限制调用来源域名。
- 生产环境可启用 `VITE_AUDIT_LOG_STRICT=true`，禁止 Edge Function 不可用时降级为浏览器直写。
- 执行 [`supabase-audit-hardening.sql`](../../supabase/sql/supabase-audit-hardening.sql) 后，`anon/authenticated` 对 `system_logs` 仅保留 SELECT 权限，直接 INSERT/UPDATE/DELETE 被撤销。
- 当前自定义 localStorage 登录态不是服务端可验证身份凭证，`operator_id` 仍由前端上报；强身份审计需要后续迁移到 Supabase Auth 或后端会话校验。

#### 表结构设计
| 数据表 | 主键 | 字段 | 说明 |
| --- | --- | --- | --- |
| `system_logs` | `id` | `operator_id`, `type`, `content`, `ip_address`, `result`, `request_id`, `user_agent`, `source`, `metadata`, `previous_hash`, `integrity_hash`, `create_time` | 系统日志与审计追踪 |

### FR-16-A 客户需求识别与排行规则

#### 识别范围
- 统计当前时间范围内全部调研表单。
- 识别对象为每张表单的基础字段与已填写问卷数据，不读取 AI 报告结果。
- 模板来源同时覆盖系统预置模板与导入后生成的模板。

#### 识别步骤
1. 根据 `survey.template_id` 取出对应调研模板。
2. 遍历模板章节与字段，仅处理“有填写值”的字段。
3. 对每个非空字段，组合以下文本作为识别输入：
   - 章节标题
   - 字段标题
   - 字段候选项
   - 字段占位说明
   - 用户填写值
4. 再补充表单基础信息：
   - `project_name`
   - `customer_name`
   - `industry`
   - `region`
5. 对每条需求规则执行识别，命中即记录该表单的需求标签。

#### 识别规则
1. 直接关键词命中
   - 若用户填写值中命中该需求的关键词，则识别为该需求。
   - 例如：`分项计量`、`电费优化` 命中“能效分析需求”。
2. 字段语义命中
   - 若字段标题或章节标题命中该需求的字段语义关键词，且该字段有填写值，则识别为该需求。
   - 例如：字段标题为“数据采集方式”，且用户已填写接入方式，则命中“数据采集接入需求”。
3. 选项命中
   - 单选/多选字段的已选项参与关键词识别。
   - 例如：已选择“碳排管理”或“对外披露”，则命中“碳管理需求”。

#### 去重规则
1. 单表单去重
   - 同一张表单内，同一需求无论命中多少次，只记 1 次。
2. 单客户去重
   - 同一客户跨多张表单命中同一需求，只记 1 次。
3. 排名统计
   - 需求排行中的 `count` = 命中该需求的去重客户数，而不是表单数。

#### 当前需求分类与关键词
| 需求分类 | 关键词示例 |
| --- | --- |
| 能效分析需求 | 能效分析、能耗分析、分项计量、负荷分析、电费优化、节能评估 |
| 数据报表需求 | 报表、报告、统计分析、数据导出、分析报告、多维分析 |
| 运维管理需求 | 运维、巡检、维保、工单、设备管理、设备健康 |
| 碳管理需求 | 碳管理、碳排、碳盘查、碳核算、双碳、ESG、对外披露 |
| 可视化需求 | 可视化、大屏、看板、驾驶舱、图形化展示 |
| 数据采集接入需求 | 数据采集、实时采集、协议转换、边缘网关、第三方系统对接、SCADA、BMS |
| 预警监测需求 | 告警、预警、异常告警、异常监测、阈值、实时监控 |
| 节能改造需求 | 节能改造、系统升级、设备替换、节能措施、改造施工 |

### FR-06-A 能力匹配与综合解决方案输出规则

#### 输入范围
- 当前调研表单基础信息与已填写问卷数据。
- 当前调研模板与关联报告模板的名称、章节、字段、正文内容。
- 系统维护的产品能力清单（能力名称、类型、适用行业、适用场景、描述）。

#### 计算规则
| 规则编号 | 规则名称 | 分值 |
| --- | --- | --- |
| R1 | 行业匹配 | `+30` |
| R2 | 已填场景命中 | `+15/项`，上限 `30` |
| R3 | 模板场景命中 | `+10/项`，上限 `20` |
| R4 | 能力名称命中问卷 | `+20` |
| R5 | 能力名称命中模板 | `+12` |
| R6 | 模板字段语义命中 | `+6/项`，上限 `18` |
| R7 | 描述关键词命中 | `+4/项`，上限 `16` |
| R8 | 模板标签加分 | 模板侧得分 `>=18` 时再 `+10` |

#### 判定阈值
- 高匹配：总分 `>= 60`
- 中匹配：总分 `>= 35`
- 低匹配：总分 `>= 20`
- 待确认：总分 `< 20`

#### 输出规则
1. 模板识别能力标签
   - 仅根据模板侧证据计算。
   - 模板侧得分达到 `18` 分即识别为一个模板能力标签。
2. 能力匹配结果
   - 输出能力名称、类型、总分、匹配等级、命中规则、证据说明。
3. 具体功能能力
   - 需优先输出命中的场景、字段、章节或关键词，不能只输出抽象能力名。
4. 综合解决方案清单
   - 优先输出“已匹配能力”与“模板已识别但待确认能力”。
   - 每项需包含：模板标签、具体功能能力、命中规则、关联建议、行动建议、方案摘要。
5. 历史报告兼容
   - 历史报告如缺失上述结构，进入报告页时自动按新规则重算并持久化。

## 6. 已知限制与改进方向

1. 密码已改为前端摘要比对并兼容历史明文记录；仍需迁移到标准认证体系和服务端会话。
2. AI 调用应迁移到服务端，避免前端密钥暴露风险。
3. 本地缓存占比较高（报告、模板覆盖、售前配置等），需逐步落库。
4. RLS 需按角色与记录归属做更细粒度策略。
